# Аким на 5 часов

Локальный симулятор: пользователь выбирает ровно пять городских мер и районы,
движок проверяет правила и бюджет, считает изменения и Astana Quality of Life Score,
AI объясняет сильные стороны, риски и компромиссы по готовым числам.

Одинаковые исходные данные и бюджет 100 для всех. Горизонт — 8 кварталов.
Детерминированная математика отделена от LLM. Без ключа работает шаблонное объяснение.
Целевой продукт — проверяемый сквозной сценарий, рабочая 3D-сцена и понятное сравнение будущих состояний с проверяемым советником. Они реализуются по зависимостям.

Источники: [TASK.md](TASK.md), [DATASET.md](DATASET.md).
Пять решений не означают по одному на каждое направление: действуют правила датасета
(максимум две меры из направления, следовательно минимум три направления).
Это подтверждается допустимым примером организаторов; исходные документы не изменены.

## Ценность для пользователя

Управленец должен не только получить балл, но и объяснить своё распределение бюджета:
какие проблемы выбранные меры уменьшают, что остаётся нерешённым и чем пришлось
пожертвовать. Симулятор помогает пройти цикл «выбрал → проверил → понял → сравнил».
Цель, показатели и правила остаются ровно такими, как у организаторов.

Фокус демонстрации: **пять решений, понятные последствия для каждого района**.
Нура и критические показатели видны потому, что минимум и штраф уже входят в
официальную формулу. Отдельный авторский рейтинг справедливости не вводится.

## Основной сценарий и критерии готовности

| Шаг | Что видит пользователь | Как проверяем |
|---|---|---|
| 1. Изучить город | Исходный Score, пять районов, конкретные показатели ниже 40, каталог всех направлений | Baseline 52.5577, Ncrit=2; S1=38 и S2=35 в Нуре |
| 2. Собрать пять решений | Меры, район для районной меры, стоимость и остаток; русские причины конфликтов | Engine проверяет весь набор; при ошибке нет нового Score и AI-запроса |
| 3. Оценить последствия | «Паспорт сценария»: пять решений, стоимость, до/после, изменение Score, слабейший район, оставшиеся критические показатели | Для официального примера: 95, остаток 5, Score 56.5431, Ncrit=0 |
| 4. Понять результат | Сильные стороны, риски и компромиссы, привязанные к рассчитанным изменениям | Demo доступен без сети; AI использует только факты из результата engine |
| 5. Сравнить варианты | Сохранённый A и новый валидный B с одинаковыми исходными данными | Оба результата посчитаны engine; указаны Score, стоимость, Ncrit и слабейший район |

Все пять шагов реализованы: форма, сохранённый A, паспорт, объяснение,
ручной/предложенный B, проверяемая ревизия и сравнение baseline/A/B в 3D.
Принимает B пользователь; ревизор показывает ухудшения и ограниченность поиска,
не объявляет глобальный оптимум. Общая приёмка R и чистая установка — отдельный этап.

## Паспорт сценария: объяснение, которое можно проверить

- Показывать `before`, `after`, `score_delta`, `cost`, `remaining_budget` из
  `SimulationResult`; числовые таблицы не извлекать из текста LLM.
- Для каждого района показывать балл до/после и фактические `indicator_deltas`.
  Отдельно отметить значения, перешедшие из `<40` в `>=40`, и оставшиеся провалы.
- Раскрывать трассировку `effects`: мера, район, показатель, эффект с лагом;
  синергии показывать отдельными строками. `effects` — прибавки до clip,
  `indicator_deltas` — изменения после clip. Не называть их вкладом в Score:
  минимум и штраф делают итоговую формулу нелинейной.
- Показывать компромисс M11: безопасность дорожного движения растёт, T1 снижается.
  Реализованный эффект берётся из engine, а не из полного эффекта каталога.
- После редактирования выбора предыдущий результат помечать как относящийся
  к сохранённому набору; текущий набор требует новой проверки и расчёта.

Это использует уже предусмотренный API v1. Изменять общие типы для паспорта не нужно.
Правила, стоимость, эффекты, лаги, синергии, порог и формула остаются в engine.

## Советник после сквозного сценария

Советник предлагает ограниченное улучшение: заменить одну меру вместе с её районом
или изменить район одной меры, сохранив ровно пять решений. Максимум 10 кандидатов
за раунд, максимум два раунда — как предусмотрено PLAN/API.

Каждый кандидат сначала проходит официальный валидатор, затем `simulate`.
Исходный вариант включён в сравнение; лучший выбирается по Score, при равном
Score — по меньшей стоимости. Пользователь видит, что изменено и какие показатели
ухудшились даже при росте общего балла. Применение — отдельным действием пользователя.

В demo кандидатов можно задавать детерминированными шаблонами, в live — предлагать
через AI; достоверность чисел в обоих случаях обеспечивает engine. Если улучшения
нет, так и написать. Результат называется «лучший из проверенных вариантов»,
а не «оптимальный для города»: ограниченный поиск не доказывает глобальный максимум.
Советник пока не реализован; его интерфейс требует отдельного API-согласования.

## Приоритеты и демонстрация

1. E1 + U1 + I1: реальный выбор и расчёт пяти решений с блокировкой ошибок.
2. A1: паспорт сценария и объяснение до/после; отказ live сохраняет demo.
3. Работающая 3D-сцена с условным макетом, получающая готовые снимки из engine.
4. Сравнение A/B, ревизор, слои и подсветка различий; полный поиск, экспорт и дополнительные анимации остаются необязательными. Случайные события не входят в модель.

Подробный план на двоих и зависимости этапов:
[IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md). Датасет и официальная цель сохраняются.

Демонстрация после I1: исходные 52.5577 и два критических показателя → официальный
пример 95 / 56.5431 / 0 → показать оставшийся бюджет и изменения в Нуре →
показать отклонение невалидного набора без расчёта → сравнить с другим валидным набором.
Рост относительно базы — сравнение по синтетической модели, а не обещание эффекта
в реальном городе. Числа второго варианта показываются только после расчёта.

Результат проверки текущей реализации и ограничения — в [REVIEW.md](REVIEW.md).
