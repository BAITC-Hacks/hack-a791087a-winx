### @alikhan: A2 — серверная часть ревизора

**Готово:** `review_scenario` доступен в `citysim/reviewer.py`; точные правила
JSON, лимитов, fallback, статусов и вызова опубликованы в [API.md](API.md).
Live-ветки проверены моками, платные запросы не выполнялись.
После A2: 144 Python-теста (25 новых), 4 JS-теста и запуск HTTP 200.

**Свои файлы:** `citysim/reviewer.py`, `tests/test_reviewer.py`.
Общий API и review_models менять только при необходимости с API-коммитом.
Не редактировать app.py, citysim/ai.py, ui/* и 3D-файлы в этом пакете.

Существующий контракт сохраняется:

```python
review_scenario(source, dataset, constraints, *, demo_mode=True,
                api_key=None, model=None) -> tuple[ReviewResult, Explanation]
```

Критерии готовности:

1. Demo без ключа и сети использует S1; source/constraints проверяются до AI.
2. Live предлагает только ID решений, максимум два раунда по 10 относительно
   первоначального A. Каждый набор проверяется через S1, числа AI игнорируются.
3. Ошибочный JSON/тип не считается проверенным кандидатом; неизвестные строковые
   ID проходят валидатор и сохраняют причины. Лимиты обеспечиваются кодом.
4. Обработаны ошибка/пустой ответ/timeout, сохранён лучший уже проверенный вариант;
   completed_limited и incomplete не смешиваются с improved/cheaper_equal/unchanged.
   Fallback явно обозначен; общий бюджет ревизии и сетевых вызовов — по плану A2.
5. Explanation объясняет именно ревизию A→B и её завершённость.
   `best.score_delta` — изменение относительно baseline, а не относительно A;
   не выдавать его за выигрыш B над A. Один explain_result(best) эту задачу не закрывает.
6. Unit-тесты с моками: demo не создаёт SDK; второй раунд сохраняет A/locked;
   отказ второго раунда сохраняет результат первого; invented Score не используется.

Эта часть не зависит от готовности новой сцены или новых кнопок.
