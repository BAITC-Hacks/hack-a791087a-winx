## Жёсткие правила хакатона (нарушение = дисквалификация)

- Работаем только в этом репозитории: его выдали организаторы через edu.astanahub.com. Никаких других репозиториев для кода проекта.
- Промежуточный результат нужен по итогам КАЖДОГО часа с 13:00 до 18:00 (GMT+5). В начале каждого хода выполни `git log -1 --author="$(git config user.email)" --format=%cr` — это время МОЕГО последнего коммита. Если прошло больше 40 минут — сначала закоммить и запушь текущее рабочее состояние (по правилам из раздела «Командная работа»), потом продолжай.
- Коммит и push после каждого законченного куска. Сообщения осмысленные: `feat: …`, `fix: …`, `docs: …`, а не «update».
- Инструменты разработки (этот AGENTS.md, конфиги, заготовки) — отдельным первым коммитом `chore: dev tooling`. Код продукта — своими коммитами.
- Дедлайн 18:00. Всё, что не запушено к 18:00, не существует. Правки после 18:00 не оцениваются.
- Любая сторонняя библиотека, модель, датасет, API, шаблон или заимствованный код → сразу строка в `THIRD_PARTY.md`: название, ссылка, лицензия, зачем. Создай файл при первой зависимости. Отдельным разделом «Инструменты разработки» перечисли использованные AI-инструменты и скиллы.
- Секреты не коммитить никогда. Ключи — в `.env` (добавлен в `.gitignore`), шаблон — в `.env.example`.

- Эксперты запускают проект сами, строго по README. Не запустилось — проект снимают, исправления не принимаются.
- Проверка не должна требовать моих личных аккаунтов и подписок. Если нужен внешний API — демо-ключ с лимитом или демо-режим с моками, который включается одной переменной окружения. Всё это описать в README.

- README.md держи актуальным с первого часа. Обязательные разделы: описание и назначение, архитектура, технологии, установка, запуск, зависимости, переменные окружения, проверка основного сценария (пошагово, с ожидаемым результатом).

## Командная работа (нас двое, каждый коммитит со своего GitHub-аккаунта)

- Кто что делает — в `docs/PLAN.md` (у каждого этапа есть владелец). Контракт между частями — в `docs/API.md`. Чужие файлы не переписывай. Нужна правка в зоне напарника — допиши запрос в `docs/HANDOFF.md`: кому, что нужно, зачем, формат данных. У себя пока сделай мок, чтобы не ждать.
- В начале каждого хода синхронизируйся:
  1. `git fetch`
  2. `git log --oneline 'HEAD..@{u}'` — что напарник запушил с прошлой синхронизации; `git diff --stat 'HEAD...@{u}'` — какие файлы он тронул.
  3. Если пришло новое — прочитай эти коммиты. В первую очередь `docs/API.md`, `docs/PLAN.md`, `docs/HANDOFF.md`, файл состояния напарника в `docs/state/`, общие типы, конфиги и зависимости.
  4. `git pull --rebase --autostash`
  5. Скажи мне в 2–3 строках: что сделал напарник, задевает ли это мою текущую задачу и что ты под это подстроил. Если поменялся контракт в `docs/API.md` — сначала подстрой мою сторону под него, потом продолжай задачу. Если в `docs/HANDOFF.md` есть запрос ко мне — сообщи о нём.
- Меняешь контракт (`docs/API.md`, общие типы, формат данных) — обнови `docs/API.md` в том же коммите и начни сообщение с `API:`, например `API: feat(progress): add level field`. Это сигнал для агента напарника.
- Перед каждым push: `git pull --rebase --autostash`, запуск и тесты, потом push.
- Никогда не делай `git push --force`, `git reset --hard` и не переписывай уже запушенную историю: подтверждаемая история разработки — требование хакатона.
- Конфликт при rebase: в своих файлах разреши сам; в коде напарника — остановись и покажи мне конфликт, не решай за него.
- Если нужного скилла (`$edu-levers`, `$idea-council` и т. п.) у тебя нет — пропусти его и работай по этим правилам.

## Сессии и память

Когда контекст разрастается, я открываю новую сессию (`/new`). Новая сессия не помнит чат — только файлы. Поэтому:

- Мой файл состояния — `docs/state/<мой ник>.md`. Ник найди в таблице «Команда» в `docs/PLAN.md` по `git config user.email`.
- Обновляй его в конце каждого этапа (в том же коммите) и когда я пишу «закрываем сессию». Перезаписывай целиком, а не дописывай в конец. До 40 строк, только проверяемые факты: файлы, команды, хэши коммитов. Разделы:
  - **Сейчас** — этап из PLAN.md, статус, последний коммит.
  - **Сделано** — что готово за эту сессию.
  - **Не закончено** — что, в каком файле, что осталось.
  - **Решения** — решение и почему. Не больше 8, устаревшие удаляй.
  - **Грабли** — что не работает, обходы, чего не делать.
  - **Проверка** — команда запуска и что должно получиться.
  - **Следующий шаг** — одно конкретное действие.
- «Закрываем сессию»: обнови файл состояния, закоммить и запушь. Если запуск сейчас сломан — только закоммить, а push сделать после починки, иначе сломаешь напарнику pull.
- Первый ход новой сессии (я пишу «новая сессия» или «продолжаем», или ты не видишь предыдущих ходов):
  1. Прочитай свой файл состояния, `docs/PLAN.md`, `docs/API.md` (если есть) и файл состояния напарника.
  2. Выполни `git status` и `git log --oneline -10`.
  3. Выполни команду из раздела «Проверка» и убедись, что написанное там правда.
  4. Перескажи мне в пяти строках: где мы, что работает, что сломано, следующий шаг. Потом продолжай работу.
- Если чат, файлы и код расходятся — верь коду и git, затем файлам в `docs/`, и только потом памяти чата. Нашёл расхождение — исправь файл состояния.

## Продукт

- ТЗ — `docs/TASK.md`, данные, формула и правила — `docs/DATASET.md`. Это источник правды.
- Все числа (эффекты мер, лаги, синергии, Score, бюджет, валидация правил) считает детерминированный код строго по формулам из `docs/DATASET.md`. LLM только объясняет уже посчитанное, сравнивает наборы и советует — числа сам не считает и не придумывает. Так требует ТЗ.
- Эталоны для тестов движка: базовый Score без мер = 52.5577 (N_crit = 2), пример из раздела 3 (M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка) = стоимость 95, Score 56.5431, N_crit = 0; самый дешёвый валидный набор стоит 61.
- Без ключа OpenAI проект работает в демо-режиме с шаблонным объяснением.
- Нужны идеи — `$idea-forge`. Проверить решение до того, как тратить на него часы, — `$idea-council` в режиме `быстрый`.
- Сначала сквозной рабочий сценарий от начала до конца, пусть некрасивый. Полировка — потом.
